# План реализации — Qalqan Safe (Демо-симуляция финтех-защиты)

Прототип мобильного банка с многоуровневой локальной защитой от очного ограбления, телефонного шантажа и вывода депозитов: изолированный субсчёт по тревожному ПИН-коду (Zero-Tell UX), поведенческий скоринг и Soft-Escrow, подтверждение «второй рукой» и детерминированный симулятор API Антифрод-центра НБРК.

## Подтверждённые параметры и архитектурные решения

> [!IMPORTANT]
> Ниже зафиксирована структура модулей, пакетов и 5-этапный план внедрения по вашей спецификации. Принятые по умолчанию детали (например, единый `AppClock` поверх системных часов для мгновенной перемотки времени в тестах и демо, а также сохранение существующего `namespace` Android-ресурсов при уникальном `applicationId`) будут дополнительно задокументированы в `DECISIONS.md`. После вашего подтверждения переходим к **Этапу 1**.

- **Стек и сборка**: Kotlin, Jetpack Compose (Material 3), Single-Activity, Navigation Compose (`kotlinx.serialization` для типобезопасных маршрутов и JSON-пакетов НБРК), Hilt DI, Coroutines/Flow, Room + SQLCipher (ключ шифрования БД в Android Keystore), `minSdk 26`, язык интерфейса — русский, валюта — KZT (`₸`).
- **Тестирование**: JUnit5 (`junit-jupiter`), Turbine (`Flow`), Room in-memory; чистый доменный движок `RiskEngine` и `Ledger` в отдельном модуле `:core-domain` без Android-зависимостей.
- **Периметр безопасности**: `FLAG_SECURE` на всех экранах (скрытие превью в recents), `allowBackup=false` и исключение БД из правил бэкапа, запрет логирования ПИН/кодов/сумм, хранение ПИН/кодов как солёных хешей (PBKDF2WithHmacSHA256). Подсказка ПИН (`1234`/`9110`) открывается долгим нажатием на логотип, демо-панель — тройным тапом (оба только при `BuildConfig.DEMO`).
- **Дополнительные правила**: тревожный перевод сверх остатка субсчёта отклоняется с «Недостаточно средств»; тревожный перевод в пределах субсчёта проводится через `ESCROW_HOLD` в Ledger (в UI `COMPLETED`); `AWAITING_SECOND_HAND` только при досрочном закрытии депозита; триггер входа по тревожному ПИН — `DURESS_LOGIN_SILENT`; рабочие дни Пн–Пт с настраиваемым списком праздников РК; `Known Limitations` в `README.md` и решения в `DECISIONS.md`.

## 1. Структура модулей и пакетов

Проект организуется в виде чётко разделённой многомодульной / многослойной архитектуры, где чистое доменное ядро (`domain` / `:core-domain`) не зависит от Android SDK, что позволяет прогонять матрицу рисков и инварианты двойной записи за миллисекунды на JVM.

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         :app (Android / Compose / Hilt)                 │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │ ui (экраны, навигация, компоненты и дизайн-система Obsidian Vault)│  │
│  │  • theme       — цвета, формы, Manrope & JetBrains Mono           │  │
│  │  • auth        — ПИН-клавиатура, блокировка попыток, долгое наз.  │  │
│  │  • home        — Главная (Standard / Zero-Tell Duress декой)      │  │
│  │  • transfers   — Переводы, коды 5555/9999, анимация НБРК, эскроу  │  │
│  │  • deposits    — Сейф и депозиты Money Lock, досрочное закрытие   │  │
│  │  • security    — Центр защиты (Настройки | Вторая рука | Монитор) │  │
│  │  • demo        — Скрытая демо-панель (время, сценарии, роли)      │  │
│  └───────────────────────────────┬───────────────────────────────────┘  │
│                                  ▼                                      │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │ presentation (ViewModel + UDF UiState / UiEvent / StateFlow)      │  │
│  └───────────────────────────────┬───────────────────────────────────┘  │
│                                  ▼                                      │
│  ┌───────────────────────────────┴───────────────────────────────────┐  │
│  │ data (Room + SQLCipher + Android Keystore + Repository + Seeder)  │  │
│  │  • crypto      — KeystoreManager (ключ БД), PinHasher (PBKDF2)    │  │
│  │  • local       — AppDatabase (SQLCipher), DAO с SessionMode       │  │
│  │  • ledger      — транзакционное проведение двойной записи         │  │
│  │  • simulator   — NbrkAntifraudApiSimulator (seeded, 800-1400ms)   │  │
│  │  • seed        — DemoSeeder (балансы, 60 дней истории, дропперы)  │  │
│  │  • repository  — фильтрация по SessionMode (Standard / Duress)    │  │
│  └───────────────────────────────┬───────────────────────────────────┘  │
└──────────────────────────────────┼──────────────────────────────────────┘

│  • clock          — AppClock (System / SimulatedClock для перемотки)    │
│  • risk           — RiskEngine, поведенческий скоринг, матрица правил   │
│  • validation     — валидатор KZ IBAN (MOD 97-10), БИН, Hamming-пин     │
│  • model          — доменные модели, SessionMode, Decision, DTO НБРК    │
```

### Почему такое разделение
- **Чистый `:core-domain` (JVM)**: `RiskEngine`, таблица решений, калькулятор расстояния Хэмминга, валидация KZ IBAN и расчёты баланса двойной записи компилируются и тестируются через JUnit5 без эмулятора и Android-контекста.
- **Изоляция `SessionMode` на уровне репозитория/DAO**: запросы в БД при активном `SessionMode.DURESS` физически возвращают только `ISOLATED_SAFE`, декой-депозит и мелкую 60-дневную историю — основные активы и таблицы инцидентов не попадают даже в `StateFlow` ViewModel.

## 2. Поведенческий скоринг, матрица решений и Zero-Tell UX

### Движок решений (`RiskEngine.evaluate(context) -> Decision`)

| Фактор риска | Баллы | Условие срабатывания |
| :--- | :---: | :--- |
| Новый получатель | `+25` | IBAN/карта отсутствует в доверенных контактах |
| Крупная сумма | `+20` | `amount >= threshold` (по умолчанию `300 000 ₸`) |
| Доля от остатка | `+15` | `amount > 70%` доступного остатка счёта |
| Ночное время | `+10` | Время по `AppClock` в интервале `23:00–06:00` |
| Список дропперов | `+30` | Совпадение реквизитов со стоп-листом симулятора |
| Недавняя смена ПИН/устройства | `+15` | Изменение безопасности за последние 24 часа |
| Частота операций | `+15` | `>= 3` исходящих переводов за последний час |
| Код шантажа (`9999`) | `= 100` | Принудительно устанавливает скоринг `100` |

**Шкала и матрица решений**:
- `0–39`: проходит (`COMPLETED`); для нового получателя — `COMPLETED` с фоновым логированием скоринга.
- `40–79`: `COOLING_OFF` (пауза 30 мин по умолчанию + уведомление «второй руке») или `AWAITING_SECOND_HAND` при досрочном закрытии депозита + крупном переводе новому получателю.
- `80+` или код `9999`: `SOFT_ESCROW_HOLD` (заморозка на внутреннем `ESCROW_HOLD`, срок проверки по умолчанию 5 рабочих дней) + пошаговая отправка индикаторов в `NbrkAntifraudApiSimulator`.
- `SessionMode.DURESS`: клиенту в UI всегда отображается успешное выполнение в рамках субсчёта (`COMPLETED`), внутри тихо фиксируются события `DURESS_PIN_LOGIN` / `DURESS_TRANSFER` и передаётся пакет в НБРК-симулятор.
- **Zero-Tell статусы**: в общем списке операций отображается нейтральное «В обработке»; реальный статус, срок проверки и разбивка риск-факторов раскрываются только в детальной карточке в обычном режиме и в кабинете «Второй руки».

## 3. Визуальная система «Obsidian Vault» и ролевой интерфейс

- **Цветовые токены**: фон `#0B0F14`, поверхность `#131A22`, вторичная поверхность `#1B2430`, обводка `#263242`, защита `#10B981`, Soft-Escrow / ожидание «второй руки» `#F59E0B`, высокий риск `#EF4444`.
- **Шрифты**: локальные `.ttf` (`Manrope` для интерфейса и заголовков, `JetBrains Mono` для сумм в `₸`, IBAN, кодов подтверждения, обратных отсчётов и JSON-пакетов НБРК).
- **Интерактивность и полировка**: `spring`-анимации переходов, цели нажатия $\ge 48\text{dp}$, пошаговая анимация связи с НБРК («Сбор индикаторов → Отправка в API → Вердикт»), постоянная плашка «Демонстрационная симуляция. Не является интеграцией с НБРК/НПК» во всех экранах монитора и настроек (полностью отсутствует в тревожном режиме).

## 4. Поэтапный план реализации (с проверкой сборки и тестами после каждого этапа)

### Этап 1 — Фундамент, безопасность БД, ПИН-вход и режимы Standard / Duress
- Настройка `:core-domain` и `:app` (Hilt, `kotlinx.serialization`, `minSdk 26`, тема «Obsidian Vault», загрузка `Manrope` и `JetBrains Mono`, кастомная иконка приложения, `FLAG_SECURE`).
- Шифрованная БД **Room + SQLCipher** с ключом в **Android Keystore**, схема всех сущностей (`AccountEntity`, `DepositEntity`, `TransferEntity`, `SecondHandRequestEntity`, `NbrkIncidentEntity`, `SecurityConfigEntity`, `LedgerEntryEntity`, `AuditLogEntity`), DAO с фильтрацией по `SessionMode`.
- Хеширование ПИН/кодов через `PBKDF2WithHmacSHA256`, защита от брутфорса (5 попыток → нарастающая пауза), проверка расстояния Хэмминга (`>= 2`) и запрет тривиальных ПИН при изменении.
- `DemoSeeder`: основной счёт `845 200 ₸`, депозиты Money Lock `8 450 000 ₸` и `1 200 000 ₸`, субсчёт `48 500 ₸`, декой-депозит `~120 000 ₸`, 60 дней мелких бытовых трат, контакты, дропперы и доверенные лица.
- Экран ПИН-клавиатуры (демо-подсказка только при `BuildConfig.DEMO` по долгому нажатию на логотип) и базовые вкладки для `Standard` и абсолютно неотличимого `Duress` (выход через кнопку блокировки в профиле).
- *Проверка*: сборка + тесты шифрования/хеширования, Хэмминг-валидации, фильтрации `SessionMode` (Room in-memory + JUnit5).

### Этап 2 — Двойная запись Ledger и чистый RiskEngine (до UI переводов)
- Реализация `LedgerService` в единой `@Transaction` с инвариантом сохранения общей суммы по всем контурам.
- Реализация чистого `RiskEngine` (все 8 факторов скоринга и полная таблица матрицы решений) и валидатора KZ IBAN/БИН.
- *Проверка*: полный набор JUnit5-тестов на каждую строку матрицы решений, граничные значения (`39/40`, `79/80`, `threshold ± 1`, `70%`, `22:59/23:00/06:00/06:01`) и тесты инварианта `Ledger` включая откат при исключении посреди транзакции. Переход дальше только при 100% зелёных тестах.

### Этап 3 — Переводы, COOLING_OFF, Soft-Escrow и Симулятор НБРК
- Экран переводов с выбором доверенного/нового получателя (валидация KZ IBAN), суммой и кодом подтверждения (`5555` / `9999`).
- Механизмы `COOLING_OFF` (30 мин) и `SOFT_ESCROW_HOLD` (перевод на `ESCROW_HOLD` через Ledger, 5 рабочих дней) с Zero-Tell «В обработке» в общем списке и детальной расшифровкой в обычном режиме.
- `NbrkAntifraudApiSimulator` (800–1400 мс seeded задержка, JSON DTO через `kotlinx.serialization`, 4 триггера) + пошаговая анимация отправки и экран **Монитор НБРК API** с раскрываемыми JSON и риск-разбивкой.
- *Проверка*: сборка + Turbine-тесты потоков переводов, Soft-Escrow, детерминированности НБРК-симулятора.

### Этап 4 — «Вторая рука» и Центр защиты
- Сценарий досрочного закрытия депозита Money Lock + крупного перевода новому получателю → создание `SecondHandRequest (PENDING)`, перевод депозита в `PENDING_EARLY_CLOSURE`, заморозка средств в Ledger.
- **Кабинет «Второй руки»**: список заявок с таймерами, просмотр инициатора, депозита, реквизитов и риск-факторов; подтверждение только после 10-минутной паузы и повторного ПИН «второй руки»; отклонение как фрод (возврат под Money Lock, `BLOCKED_FRAUD`, срочный пакет в НБРК); авто-таймаут 24 часа (`EXPIRED`); поддержка резервного доверенного лица; Zero-Tell при тревожном режиме.
- **Конфигурация Центра защиты**: смена ПИН/кодов (с проверкой Хэмминга), лимит субсчёта, порог крупной суммы, выбор основного/резервного контакта «второй руки», журнал аудита (`AuditLogEntity`).
- *Проверка*: сборка + интеграционные Room in-memory и Turbine-тесты жизненного цикла «Второй руки» (пауза 10 мин, таймаут 24 ч, откат при отклонении, резервное лицо).

### Этап 5 — Демо-панель, перемотка времени, сквозные сценарии и полировка
- Скрытая демо-панель (активация по долгому нажатию на логотип / спец-жесту при `BuildConfig.DEMO`):
  - Перемотка `SimulatedClock`: `+1 час`, `+1 день`, `+5 рабочих дней` (мгновенный пересчёт `COOLING_OFF`, Soft-Escrow и 10-мин / 24-ч таймеров «Второй руки»).
  - Переключатель ролей (Клиент / Вторая рука / Инспектор НБРК), кнопка полного сброса демо-данных.
  - Три автоматических сквозных сценария («Ограбление», «Шантаж по телефону», «Вывод депозита через Вторую руку») с прогоном $< 2$ мин.
- Финальная проверка критериев приёмки: аудит Zero-Tell строк/UI, проверка отсутствия демо-подсказок в release-сборке, полный прогон тестов и релизная/дебаг-компиляция.
