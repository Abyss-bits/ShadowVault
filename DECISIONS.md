# Архитектурные и продуктовые решения (DECISIONS.md)

Документ фиксирует ключевые решения, принятые перед началом реализации прототипа **Qalqan Safe**.

## 1. Тревожный перевод сверх остатка изолированного субсчёта
- **Решение**: Если клиент в тревожном режиме (`SessionMode.DURESS`) пытается перевести сумму, превышающую реальный остаток изолированного субсчёта (`ISOLATED_SAFE`), операция отклоняется со стандартным банковским ответом «Недостаточно средств на счёте».
- **Обоснование**: Поддержка Zero-Tell UX — поведение должно быть полностью неотличимо от обычного банковского приложения и не провоцировать раскрытие скрытых депозитов.

## 2. Проведение тревожного перевода через Ledger и UI
- **Решение**: Исходящий перевод в пределах доступного остатка в `SessionMode.DURESS` проводится через внутренний счёт удержания (`ESCROW_HOLD`) в единой `@Transaction` двойной записи `LedgerEntryEntity`, но в UI тревожного режима отображается со статусом успешной/стандартной отправки (`COMPLETED`), при этом тихо отправляется индикатор в `NbrkAntifraudApiSimulator`.
- **Обоснование**: Инвариант сохранения общей суммы средств по всем счетам и депозитам соблюдается строго, средства фактически не покидают контур банка, а экран не выдаёт защитный сценарий.

## 3. Разграничение `AWAITING_SECOND_HAND`, `COOLING_OFF` и крупного перевода известному получателю
- **Решение**:
  - `AWAITING_SECOND_HAND` назначается **только** при сценарии с источником «досрочное закрытие депозита» (`EARLY_DEPOSIT_CLOSURE`) в сочетании с новым получателем и суммой $\ge$ порога.
  - Остальные переводы со скорингом `40–79` (не вызванные кодом шантажа `9999` и не достигающие `80+`) получают `COOLING_OFF` (пауза по умолчанию `30` минут + уведомление «второй руке»).
  - Если сумма $\ge$ порога, получатель **известный** (из списка доверенных контактов), а скоринг `< 40`, перевод переходит в `COMPLETED` после повторного ввода кода подтверждения перевода (`5555`).
- **Обоснование**: Исключает неоднозначность между ветками матрицы решений и позволяет покрыть каждую строку матрицы строгими юнит-тестами.

## 4. Единое имя триггера входа по тревожному ПИН-коду
- **Решение**: Для события входа по тревожному ПИН-коду используется единый идентификатор триггера `DURESS_LOGIN_SILENT` (вместо `DURESS_PIN_LOGIN`) во всех моделях, DTO симулятора НБРК, логах БД и тестах.
- **Обоснование**: Сквозная согласованность контракта между доменом, базой данных и монитором API НБРК.

## 5. Расчёт рабочих дней для сроков проверки (Soft-Escrow)
- **Решение**: Рабочими днями считаются понедельник–пятница (`DayOfWeek.MONDAY..FRIDAY`). Праздничный календарь Республики Казахстан представлен как настраиваемый список дат `Set<LocalDate>` (по умолчанию пустой, конфигурируемый в `BusinessCalendar` / настройках).
- **Обоснование**: Детерминированное поведение `AppClock` при перемотке времени (`+5 рабочих дней`) в демо и тестах без привязки к внешним источникам.

## 6. Политика бэкапа, логирования и защиты от скриншотов
- **Решение**:
  - В `AndroidManifest.xml` задано `android:allowBackup="false"`.
  - В `backup_rules.xml` и `data_extraction_rules.xml` явно исключена зашифрованная база данных и файлы конфигурации безопасности.
  - На уровне приложения и логгера запрещено логировать ПИН-коды, коды переводов и суммы операций (даже в `debug`).
  - `WindowManager.LayoutParams.FLAG_SECURE` принудительно включён на `Activity` во всех `release`-сборках (`!BuildConfig.DEMO`) для блокировки скриншотов, записи экрана и скрытия превью в `recents`. В `debug`-сборке (`BuildConfig.DEMO = true`) по умолчанию отключён, чтобы потоковый видеозахват Streaming Emulator не показывал чёрный экран, и может быть включён переключателем в демо-панели.

## 7. Разделение жестов для демо-подсказки и демо-панели
- **Решение**:
  - Подсказка демо-ПИНов и ролей на экране входа (`1234` / `9110` / вход «Второй руки») открывается **долгим нажатием на логотип** и компилируется только при `BuildConfig.DEMO == true` (отключено в `release`).
  - Скрытая демо-панель (перемотка времени, сброс данных, 3 сквозных сценария, переключатель ролей) открывается **тройным тапом** по логотипу / заголовку (также только при `BuildConfig.DEMO == true`).
- **Обоснование**: Исключает случайное открытие служебной панели при демонстрации экрана входа и разделяет два независимых сценария показа.

## 8. Модуль чистого домена и локальные допущения
- **Решение**:
  - Чистая бизнес-логика (`RiskEngine`, `AppClock`, модели `Ledger`, валидаторы KZ IBAN/БИН, проверки Хэмминга) выносится в отдельный JVM-модуль `:core-domain` с тестами JUnit5 (`junit-jupiter`).
  - База данных шифруется через `net.zetetic:sqlcipher-android` с 256-битным ключом, сгенерированным и обёрнутым через `AndroidKeyStore` (`AES/GCM/NoPadding`).
  - Имя приложения в ресурсах и `metadata.json`: `Qalqan Safe`. `namespace` Android-ресурсов остаётся `com.example`, `applicationId` задаётся уникальным (`com.aistudio.qalqansafe.kxmpzq`).
