# Qalqan Safe — Прототип активной антифрод-защиты мобильного банка

**Qalqan Safe** — демонстрационное Android-приложение (Kotlin, Jetpack Compose, Material 3), моделирующее многоуровневую защиту клиента от очного ограбления, телефонного шантажа (социальной инженерии) и несанкционированного досрочного вывода депозитов.

> **Важно**: Это **демонстрационная симуляция** на локальной зашифрованной базе данных. Приложение **не** подключено к реальному контуру НБРК / АО «НПК» и не выполняет реальных банковских переводов.

## Ключевые механизмы (по этапам)
- **Скрытый сейф (Duress PIN / Zero-Tell UX)**: тревожный ПИН открывает изолированный субсчёт (`48 500 ₸`), декой-депозит и 60-дневную историю мелких трат, полностью скрывая основные средства на уровне репозитория/DAO.
- **Поведенческий скоринг и матрица решений (`:core-domain`)**: чистая Kotlin-логика оценки риска `0–100`, правила `COOLING_OFF`, `SOFT_ESCROW_HOLD` и `AWAITING_SECOND_HAND`.
- **Задержанный клиринг (Soft-Escrow) и Симулятор API НБРК**: заморозка подозрительных переводов во внутреннем эскроу через двойную запись `Ledger` с детерминированной имитацией REST-пакетов в Антифрод-центр.
- **«Вторая рука»**: подтверждение досрочного закрытия депозита Money Lock + крупного перевода новому получателю через доверенное лицо (пауза 10 мин, повторный ПИН, таймаут 24 ч, резервный контакт).

## Стек
- Kotlin, Jetpack Compose (Material 3), Navigation Compose (`kotlinx.serialization`)
- Hilt DI, Coroutines & StateFlow (MVVM + UDF)
- Room + SQLCipher (ключ в Android Keystore), PBKDF2WithHmacSHA256 для ПИН/кодов
- Чистый JVM-модуль `:core-domain` с JUnit5 (`junit-jupiter`) + Turbine + Room in-memory

## Демо-доступ (только в `debug` / `BuildConfig.DEMO`)
- **Долгое нажатие на логотип** на экране входа: показать подсказку ПИН-кодов (`1234` — обычный, `9110` — тревожный, `5555` / `9999` — коды перевода).
- **Тройной тап по логотипу**: открыть скрытую демо-панель (перемотка времени, сброс данных, сценарии и переключатель роли).

## Known Limitations (Известные ограничения прототипа)
1. **Рутованное устройство / скомпрометированная ОС**: на устройствах с root-доступом, отладчиком ядра или модифицированным фреймворком злоумышленник с физическим или системным доступом способен перехватить память процесса, обойти `FLAG_SECURE` или извлечь ключ из пользовательской сессии. Приложение не заменяет аппаратную аттестацию (Play Integrity / StrongBox) в продакшене.
2. **Один процесс и локальное хранение ролей**: «Клиент», «Доверенное лицо (Вторая рука)» и «Инспектор API НБРК» работают в одном локальном приложении и одной локальной БД Room+SQLCipher. В реальной банковской системе кабинет «Второй руки» и контур фрод-мониторинга должны располагаться на независимых устройствах и серверах.
3. **Симуляция Антифрод-центра НБРК**: `NbrkAntifraudApiSimulator` формирует детерминированные JSON-пакеты и имитирует задержку ответа (`800–1400 мс`) локально; реальные интеграции с АО «НПК» требуют сертифицированного закрытого канала, mTLS и ЭЦП/подписи сообщений.
4. **Симулируемое время (`AppClock`)**: перемотка времени в демо-панели меняет виртуальные часы процесса для демонстрации `COOLING_OFF` и таймаутов «Второй руки»; в реальном банке отсчёт времени ведётся исключительно на доверенном сервере.
5. **Оффлайн-архитектура без серверной телеметрии**: при очном ограблении в реальной системе тихий сигнал тревоги (`DURESS_LOGIN_SILENT`) должен доставляться по внешнему сетевому каналу; в демо-прототипе он фиксируется в локальном журнале для последующего просмотра в режиме Инспектора НБРК.
